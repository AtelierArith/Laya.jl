# LayaMLX

The Laya `DecisionModel` forward pass (ModernBERT encoder + decision head, from
`extern/laya-mlx/laya_mlx/model.py`) running on Apple's MLX through the mlx-c C API,
called from Julia with `ccall`. It covers the model only. The tokenizer, prompt building and
calibration are in the pure-Julia `Laya` package (`..`), and `bench.jl` shows how the two
fit together.

## Setup

- mlx-c is the submodule `../deps/mlx-c`, pinned at `ebc88f1` (the `main` commit that supports
  MLX v0.32.2; no release does yet). `../deps/build.sh` builds it into `../deps/usr` against the
  MLX of the `extern/laya-mlx` venv. `libmlxc.dylib` finds `libmlx.dylib` through an absolute
  rpath into that venv, so the venv must exist. See `../SETUP.md` for all steps.
- To use another build, set `LAYAMLX_LIBMLXC=/path/to/libmlxc.dylib` before loading the package.
- `julia --project=LayaMLX -e 'using Pkg; Pkg.instantiate()'`

```julia
using LayaMLX
m = LayaMLX.load(dir; dtype=Float32, device=:gpu)   # Float16, MX.BFloat16; :gpu or :cpu
logits, action = m(batch)                             # batch: Laya.collate / reference collate Dict
logits, action, tr = LayaMLX.forward(m, batch; trace=true)
```

`batch` uses the Julia layout (`input_ids` and `attention_mask` are `(L, n)`, `marker_pos`
and `marker_mask` are `(K, n)`, `qtype` is `(n,)`, and ids and positions are 0-based). The
function returns Float32 `logits` `(K, n)` and `action` `(A, n)`. The trace Dict has the same
keys and sizes as `LayaMLXReference.trace`: `embeddings`, `mask_full`, `mask_sliding`,
`layer_i`, `encoder`, `typed`, `head_i`, `logits` and `action`.

## Layout

| file | contents |
|---|---|
| `gen/` | Clang.jl generator: `cd gen && julia --project=. generator.jl` rewrites `src/LibMLX.jl` from `deps/usr/include/mlx/c/mlx.h`. Rerunning it gives a file identical to the checked-in one. |
| `src/LibMLX.jl` | Raw bindings generated by Clang.jl (not hand-written). They cover every function in the mlx-c headers. The library path comes from `ENV["LAYAMLX_LIBMLXC"]` and defaults to `<repo>/deps/usr/lib/libmlxc.dylib`. |
| `src/mlx.jl` | Module `MX`, the high-level layer. Details are below. |
| `src/model.jl` | Config parsing (`EncoderConfig.from_dict` rules), `sanitize_weights`, strict weight loading (names and shapes), and the forward pass with trace. |
| `test/runtests.jl` | Op tests, a layer-by-layer comparison on the tiny checkpoint, and the real checkpoints. |
| `bench.jl`, `bench/Project.toml` | End-to-end benchmark (same JSON schema as `benchmark/bench_julia.jl`, backend `julia-mlxc-gpu`). |
| `results/` | Light benchmark runs (`short:1,short:10`, 1 warmup, 3 iterations). |

What `MX` (`src/mlx.jl`) provides:

- **`MLXArray`**: an `mlx_array` handle with a finalizer.
  - `MLXArray(::Array)` and `Array(::MLXArray)` reverse the shape and never permute data.
  - `shape(x)` is the MLX shape, and `size(x)` is its reverse.
- **dtypes**: a dtype map for Bool, UInt8, UInt32, Int8, Int16, Int32, Int64, Float16, Float32, Float64 and `MX.BFloat16`.
- **Streams**: `set_device!` and `with_device(:gpu|:cpu)` select the stream.
- **Errors**: errors go through `mlx_set_error_handler` and are raised as `MLXError` with MLX's message.
- **Ops**: the ops `model.py` uses, with MLX axes (0-based) and Python-style weak scalars:
  - elementwise arithmetic, comparison and logic, `where`
  - `matmul`, `addmm`
  - `reshape`, `transpose`, `slice`, `index`, `take`, `embedding`
  - `split`, `concatenate`, `stack`, `sum`, `softmax`, `sort`, `arange`
  - `fast.layer_norm`, `fast.rope`, `fast.scaled_dot_product_attention`
  - `relu` and `gelu`, which are `mx.compile(shapeless=true)`d through `mlx_compile` like `mlx.nn`'s, so the fused kernels match bit for bit
- **Loading**: `load_safetensors`.
- **Memory**: `clear_cache`, `active_memory`, `peak_memory` and `version`.
- **`MX.scoped(f)`**: frees every `MLXArray` created while `f` runs. Julia's GC cannot see
  device memory, so without it a forward pass's intermediates pile up until the next GC.
  `forward` runs inside `scoped`. Before this, repeated batches of 10 slowed from 330 ms to
  over 800 ms.

## Tests

```bash
julia --project=LayaMLX/test LayaMLX/test/runtests.jl                       # ops + tiny (~13 s)
LAYAMLX_TEST_REPOS=aac6fef/laya-mlx LAYAMLX_TEST_DTYPES=float32 \
    julia --project=LayaMLX/test LayaMLX/test/runtests.jl                   # one real checkpoint
```

- **Real checkpoints**: they are skipped unless `LAYAMLX_TEST_REPOS` names one, and only one
  repository is allowed per process. `LAYAMLX_TEST_DTYPES` defaults to `float32,float16`, and
  the models are freed between dtypes. Running one dtype per process is the most
  memory-friendly option.
- **Test environment**: PythonCall lives only there. `test/LocalPreferences.toml` points it at
  the `extern/laya-mlx` venv.
- **Checks**:
  - Every traced stage, as a relative error: the max abs error over valid tokens divided by
    max |reference|.
  - The masks, exactly.
  - The selected answers: the argmax over each question's valid options, and the act decision.

### Measured tolerances (MLX GPU; the reference is Python `laya_mlx` on the same device)

| checkpoint | dtype | seq lens | embeddings … layer_27 … encoder, head, logits, action |
|---|---|---|---|
| tiny (random, 3 layers) | float32, GPU and CPU | 28, 87 | 0.0 at every stage |
| aac6fef/laya-mlx (421M, 28 layers) | float32 | 47, 157 | 0.0 at every stage |
| aac6fef/laya-mlx | float16 | 47, 157 | 0.0 at every stage |
| aac6fef/laya-multilingual-mlx (322M, 22 layers) | float32 | 45, 155 | 0.0 at every stage |
| aac6fef/laya-multilingual-mlx | float16 | 45, 155 | 0.0 at every stage |

- **Why bit-identical**: the port is bit-identical to Python because it issues the same MLX
  kernels with the same arguments. That includes compiled `gelu` and `relu`, `addmm` for biased
  linears, and weak-scalar dtype rules.
- **Asserted bounds**: the tests assert looser bounds, `3e-5` (fp32) and `1e-2` (fp16), so a
  future MLX kernel change does not break them spuriously.
- **Answers**: the selected answers match in every case.

Max RSS of the test processes (`/usr/bin/time -l`), one checkpoint per process, with
LayaMLX and the Python reference both loaded:

| run | max RSS |
|---|---|
| ops + tiny | 0.86 GB |
| laya-mlx fp32 | 2.24–2.28 GB |
| laya-mlx fp16 | 2.98 GB |
| multilingual fp32 | 2.26 GB |
| multilingual fp16 | 2.86 GB |

Metal buffers are only partly visible in RSS. MLX reports a peak of 4.2 GB for the fp32
benchmark.

## Benchmark

```bash
julia --project=LayaMLX/bench -e 'using Pkg; Pkg.instantiate()'
julia --project=LayaMLX/bench LayaMLX/bench.jl --model aac6fef/laya-mlx --dtype float32 \
    --workloads short:1,short:10 --iterations 3 --warmup 1 \
    --output LayaMLX/results/aac6fef_laya-mlx-float32-julia-mlxc-gpu.json
julia --project=benchmark benchmark/compare.jl <dir with the json files>
```

- **What `bench.jl` reuses**: `Laya.prepare` and `Laya.collate` through a
  `Laya.Agent` whose CPU model is an empty stub, so no CPU weights are loaded. It also reuses
  the calibration helpers.
- **What it copies**: the post-processing loop of `Laya.predict`, with the forward pass
  swapped for LayaMLX. `predict` is typed on `Agent{T}` with a CPU `DecisionModel{T}`, so it
  cannot be called directly.
- **What the timings include**: `forward` covers upload, MLX evaluation and the copy back to
  Julia.

Apple M4, aac6fef/laya-mlx, sequence length 93, p50 over 3 iterations after 1 warmup. The
python-mlx-gpu and julia-cpu rows come from `benchmark/results/`.

| dtype | backend | workload | forward p50 ms | e2e p50 ms | vs python | answers |
|---|---|---|---:|---:|---:|---|
| float32 | python-mlx-gpu | short:1 | 41.3 | 41.7 | – | – |
| float32 | julia-mlxc-gpu | short:1 | 41.6 | 42.1 | 1.01× | same |
| float32 | julia-cpu | short:1 | 318 | 317 | 7.6× | same |
| float32 | python-mlx-gpu | short:10 | 324.5 | 329.3 | – | – |
| float32 | julia-mlxc-gpu | short:10 | 327.0 | 327.5 | 0.99× | same |
| float32 | julia-cpu | short:10 | 3021 | 3128 | 9.5× | same |
| float16 | julia-mlxc-gpu | short:1 | 33.2 | 33.2 | – | – |
| float16 | julia-mlxc-gpu | short:10 | 246.6 | 249.2 | – | – |

- **Load time**: about 1.1 s, against 0.32 s for Python (this includes compiling Julia code on first use).
- **Max RSS** of the benchmark process: 1.58 GB (fp32) and 1.58 GB (fp16).

## Known gaps

- There is no tokenizer or prompt builder here (by design). End-to-end use goes through
  `Laya` as in `bench.jl`. A proper `Laya` backend hook would remove the copied
  `predict` loop.
- The forward pass runs eagerly. Only `gelu` and `relu` are compiled, as in Python. The whole
  model is not `mx.compile`d, again as in Python.
- `MX.scoped` and the arena are per task. `MLXArray`s created inside a scope must not escape it.
- bfloat16 loads (`dtype=MX.BFloat16`) but has not been compared against the reference.
- Only the ops `model.py` needs are wrapped at a high level. Everything else is reachable
  through `LayaMLX.LibMLX`.
- `libmlxc.dylib` depends on the Python venv's `libmlx.dylib` through an absolute rpath.
